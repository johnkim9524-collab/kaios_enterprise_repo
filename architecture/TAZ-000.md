Version: 2.0
Status: APPROVED FOR IMPLEMENTATION
Owner: Atlas (KPMO)
Program Owner: John
Implementer: Codex

---

## 1. Purpose

Trust Architecture Zero(TAZ)는 Intelligence Holdings Platform 전반에서 **trust, authority, receipt, provenance, evidence, dispatch의 경계를 단순하고 검증 가능하게 유지하기 위한 공통 Architecture Constitution**이다.

TAZ의 목적은 새로운 거대 control plane을 만드는 것이 아니다. 이미 존재하는 Receipt, Provenance, Immutable Evidence, Evidence Ledger, Trusted Merge를 보존하면서, 그 위에 최소한의 contract와 adapter를 추가해 provider와 execution을 안전하게 연결하는 것이다.

본 문서는 모든 하위 TAZ 문서와 구현의 최상위 규칙이다. 하위 구현이 본 문서와 충돌하면 본 문서가 우선한다.

## 3. Requirements

### CZ-001 — Preserve Existing Trust Assets

다음 자산은 TAZ 도입을 이유로 의미론을 변경하지 않는다.

- Receipt
- Provenance
- Immutable Evidence
- Evidence Ledger
- Trusted Merge
- Audit Trail

기존 contract 변경이 불가피하면 하위 구현에서 직접 수정하지 않고 architecture change로 승격한다.

### CZ-002 — Minimal Shared Core

Shared Core에는 vertical business logic, provider-specific logic, portal logic를 넣지 않는다.

### CZ-003 — Explicit Trust Boundary

외부 Provider, serialized payload, runtime input은 검증 전까지 untrusted다.

### CZ-004 — Explicit Authority

검증된 receipt나 trusted actor만으로 protected action 권한이 생기지 않는다. Authority는 명시적 contract로 검증한다.

### CZ-005 — Fail Closed

schema/version/authority/receipt 검증이 불가능하거나 모호하면 allow가 아니라 reject/deny/block한다.

### CZ-006 — Determinism

동일한 immutable inputs와 evaluation context는 동일한 trust/authority 결과를 생성해야 한다.

### CZ-007 — Idempotency and Replay Safety

동일 logical receipt, authority evaluation, dispatch request의 재실행은 duplicate side effect를 만들지 않아야 한다.

### CZ-008 — No Silent Escalation

Adapter나 lower layer가 trust, authority, scope, capability를 암묵적으로 확대해서는 안 된다.

### CZ-009 — Versioned Contracts

Breaking change는 기존 contract를 덮어쓰는 방식이 아니라 명시적 version 변경으로 수행한다.

### CZ-010 — Auditability

중요 state transition과 allow/deny/reject decision은 traceable reason과 immutable reference를 남긴다.

### CZ-011 — Protected Gate Preservation

Production/Public/G5, 법·보안 비가역 변경, 외부 지출 등 기존 Program Owner 승인 게이트는 TAZ가 대체하거나 우회하지 않는다.

### CZ-012 — No Architecture-by-Implementation

Codex는 구현 편의를 위해 Architecture를 변경하지 않는다. 충돌은 blocker로 반환하고 architecture 문서에서 먼저 해결한다.

## 4. Interfaces

TAZ logical flow는 다음과 같다.

```text
Actor / Task
  ↓
Trust Controller (TAZ-001)
  ├── Receipt Adapter (TAZ-002) → Existing Receipt / Provenance / Evidence
  ├── Authority Contract (TAZ-003)
  └── Dispatch Adapter (TAZ-004, follow-up)
         ↓
     Provider Adapter (TAZ-005, follow-up)
         ↓
      Provider / Runtime
```

Boundary rule:

- Trust Controller는 provider-native payload를 직접 해석하지 않는다.
- Receipt Adapter는 authority decision을 내리지 않는다.
- Authority Contract는 receipt canonicalization을 수행하지 않는다.
- Dispatch/Provider Adapter는 trust 또는 authority를 자체 생성하지 않는다.
- 모든 교차 모듈 통신은 versioned contract를 통해 수행한다.

Architecture ownership:

```text
Program Owner: John
  - GO / HOLD / STOP
  - protected approval gates

Architecture Authority: Atlas (KPMO)
  - architecture contracts
  - trust model
  - acceptance / red-team review

Implementation Authority: Codex
  - implementation
  - tests
  - regression
  - architecture change authority 없음
```

## 5. Data Model

TAZ는 하나의 거대 shared object를 정의하지 않는다. 각 module은 자신의 versioned contract를 갖고 immutable references로 연결한다.

공통 최소 식별자는 다음이다.

```typescript
interface TazTraceContext {
  traceId: string
  taskId?: string
  sessionId?: string
}

interface VersionedReference {
  id: string
  version: string
}
```

공통 data rules:

1. `traceId`는 end-to-end decision chain을 연결한다.
2. receipt/evidence/authority는 mutable object copy가 아니라 immutable reference를 우선한다.
3. secret/token/credential을 shared contract에 복제하지 않는다.
4. time fields는 timezone-aware canonical representation을 사용한다.
5. unknown field/version을 permissive하게 trust하지 않는다.
6. canonical identifiers는 재현 가능하고 충돌에 안전해야 한다.

## 6. State Machine

TAZ 전체의 논리 상태는 다음과 같다.

```text
UNTRUSTED_INPUT
  ↓ receipt adaptation / validation
RECEIPT_VERIFIED
  ↓ authority evaluation
AUTHORIZED
  ↓ controller decision
READY_FOR_DISPATCH
  ↓ dispatch
DISPATCHED
  ↓ terminal receipt/evidence
FINISHED
```

Failure branches:

```text
receipt invalid       → BLOCKED
missing/invalid auth  → BLOCKED
revoked/expired auth  → BLOCKED
unknown schema        → BLOCKED
runtime error         → FAILED
explicit owner HOLD   → HOLD
```

중요 규칙:

- `RECEIPT_VERIFIED`는 `AUTHORIZED`와 동일하지 않다.
- `AUTHORIZED`는 Production/Public/G5 승인과 동일하지 않다.
- `DISPATCHED`는 성공 증거가 아니다. terminal receipt/evidence가 별도로 필요하다.
- 실패를 성공 상태로 자동 복구하지 않는다. 새 validated input/evaluation을 통해 다시 진입한다.

## 7. Error Model

TAZ error는 module-specific code를 사용하되 공통 class를 유지한다.

```text
VALIDATION_ERROR
AUTHORITY_DENIED
TRUST_BLOCKED
UNSUPPORTED_VERSION
INTEGRITY_ERROR
REPLAY_CONFLICT
RESOURCE_LIMIT
DEPENDENCY_ERROR
RUNTIME_FAILURE
PROTECTED_GATE_HOLD
```

공통 규칙:

- exception 또는 unknown state는 allow로 fallback하지 않는다.
- error는 `traceId`, module, reason code, safe diagnostics를 포함한다.
- secret/credential/raw sensitive payload를 error에 포함하지 않는다.
- terminal failure는 audit trail에 남긴다.
- 같은 원인에 대해 module마다 상충하는 allow/deny 의미를 정의하지 않는다.

## 8. Security Requirements

1. Zero implicit trust: 외부 입력·provider metadata·serialized authority는 검증 전 untrusted.
2. Default deny: 명시적 권한이 없으면 protected action deny.
3. Least privilege: capability와 scope는 최소화.
4. Immutable evidence: 기존 evidence/provenance chain을 덮어쓰지 않음.
5. Replay safety: idempotency/replay key와 conflict 검증.
6. Canonicalization safety: encoding/order/number/string 표현의 모호성 제거.
7. Version safety: unknown/breaking version fail closed.
8. Secret hygiene: API key/token/credential을 receipt/audit/shared DTO에 복제 금지.
9. Resource bounds: parser/input size/depth/time limits.
10. Delegation safety: authority delegation은 parent보다 넓어질 수 없음.
11. Protected gate safety: owner approval requirement를 generic authority로 우회 금지.
12. Dependency isolation: provider/portal/business logic가 trust core에 침투하지 않음.

## 9. Acceptance Tests

### AT-000-001 — Existing Trust Assets Preserved

TAZ 구현 전후 Receipt, Provenance, Evidence Ledger, Trusted Merge의 기존 regression이 PASS해야 한다.

### AT-000-002 — Receipt Is Not Authority

Valid receipt만 존재하고 authority가 없으면 protected dispatch는 BLOCKED.

### AT-000-003 — Authority Is Not Trust Evidence

Valid authority만 존재하고 required receipt/evidence가 없으면 trust-required dispatch는 BLOCKED.

### AT-000-004 — Unknown Version Fails Closed

TAZ-001/002/003 중 unknown breaking version input은 allow되지 않는다.

### AT-000-005 — Deterministic Decisions

동일 immutable inputs에서 반복 실행 시 canonical receipt, authority decision, controller decision이 동일해야 한다.

### AT-000-006 — Replay Does Not Duplicate Side Effects

동일 logical request 재실행으로 duplicate provider action이나 duplicate logical receipt가 발생하지 않는다.

### AT-000-007 — Provider Cannot Escalate

Provider payload의 role/trust/permission field가 core authority로 승격되지 않는다.

### AT-000-008 — Protected Gate Preserved

Production/Public/G5 및 owner-only approval 조건이 TAZ internal allow만으로 해제되지 않는다.

### AT-000-009 — Module Isolation

Trust core가 provider API, portal, business logic, repository mutation에 직접 의존하지 않는다.

### AT-000-010 — Full Trace

한 transaction의 receipt validation → authority decision → controller decision → dispatch 결과가 하나의 trace chain으로 추적 가능해야 한다.
