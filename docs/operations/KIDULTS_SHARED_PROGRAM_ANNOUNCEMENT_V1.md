## 1. Official announcement

Effective immediately, KIDULTS will no longer be operated as a collection of isolated chat sessions or independent implementation projects.

KIDULTS is now operated as **one integrated intelligence program** with three parallel but contractually connected workstreams:

1. **Track A — Kidults 120 Score**
2. **Track B — Rankability Gate**
3. **Track C — Portal V502 & Data Connection**

The three tracks remain operationally independent in their assigned responsibilities, but they share one program language, one registry system, one snapshot identity, one decision structure and one release gate.

> **One Program. One Language. One Standard. One Source of Truth.**

The Portal is not the intelligence engine. It is the presentation layer.  
Track A produces intelligence candidates.  
Track B independently validates rankability.  
Track C renders only approved, versioned intelligence.  
The Program Owner decides material strategy, provider commitment, residual risk and Production promotion.

---

## 2. Why this operating model is required

KIDULTS is simultaneously addressing:

- What Right Data is actually required
- How much data is sufficient
- Whether rankings are defensible before market-data spend
- Whether the system survives stress and scale
- How providers should be evaluated and contracted
- How intelligence should become Portal, Research and Archive outputs
- How the platform can become globally scalable and increasingly autonomous

These questions cannot be solved by one track in isolation.

The purpose of this operating model is to prevent:

- Different AI agents using different assumptions
- Portal design driving intelligence conclusions
- Rankability judgments using stale snapshots
- Provider spend preceding measured data requirements
- New doctrine existing only inside a chat session
- Untraceable changes, duplicated work and late-stage integration failure

## 3. Program operating flow

```text
Track A: 120 Score snapshot candidate
        ↓
Track B: independent rankability assessment
        ↓
Integration Gate: contract, evidence, assets, rights and QA
        ↓
Track C: Portal V502 release manifest and rendering
        ↓
Program Owner: Production decision
        ↓
Published Snapshot → Portal → Research → Archive
```

### Mandatory separation of duties

```text
Generate ≠ Validate ≠ Approve ≠ Publish
```

- Track A generates candidates.
- Track B validates rankability.
- Integration functions validate contracts, assets and QA.
- The Program Owner approves Production.
- The Snapshot Publisher publishes the approved package.
- Track C renders the published result.

No single actor may generate, validate, approve and publish the same material capability without independent gates.

# 6. Handoff Rules

Every cross-track handoff must state:

- `handoff_id`
- From track
- To track
- `snapshot_id`
- Artifact path or issue reference
- Artifact version
- Requested decision or action
- Deadline
- Known limitations
- Acceptance criteria

### Acceptance rule

The receiving track explicitly accepts, rejects or requests correction. Silence is not acceptance.

### Mutation rule

The receiver does not directly modify the producer-owned artifact. Corrections are requested from the owner or made through a versioned contract change.

### Snapshot rule

A handoff is invalid if the snapshot ID differs from the artifact chain under review.
