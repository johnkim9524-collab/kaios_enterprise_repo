# KIDULTS Live Intelligence POC & Future Portal Blueprint

Status: CANONICAL DESIGN BASELINE
Date: 2026-08-10
Authority: KIDULTS 120 / Issue #210

## 1. Decision
KIDULTS will run two tracks in parallel:

A. REAL EXTERNAL DATA POC — collect only rights-cleared, decision-useful external observations and prove the intelligence loop against real-world volatility, missingness, provenance, latency, and source failure.
B. FUTURE PORTAL SHELL — freeze a durable collector/institution playground architecture now, so new intelligence products plug into stable slots instead of repeatedly redesigning the UI.

The portal is a PRODUCT SHELL, not a page assembled around today's available data.

## 2. Value-before-data POC objective
The POC must prove this chain:
Customer Curiosity -> Decision Value -> Intelligence Question -> Required Signal -> Rights-Cleared Source -> Observation -> Entity -> Time Series -> Signal -> WHY -> Confidence -> Product Surface.

Raw collection volume is not a success metric.

## 3. Initial POC scope
### Candidate universe
- target registry: >=300 candidate objects
- first live cohort: >=100 distinct candidate objects with repeatable external observations
- preserve 8 Core Categories as current operating taxonomy, but allow dynamic category expansion under the canonical admission rules

### Intelligence primitives
1. Identity / Provenance
2. Scarcity / Supply
3. Transaction / Price / Comparable
4. Liquidity
5. Demand / Attention
6. Canon / Institutional / Cultural
7. Risk / Confidence

### WHY contract
Every material insight should converge on:
WHAT changed -> WHY -> supporting evidence -> counter-evidence -> confidence -> SO WHAT -> WHAT NEXT -> invalidation condition.

No channel is activated merely because it is public. Each source requires documented collection rights/method, allowed fields, provenance, refresh cadence, retention/derived-data position, quality, economics, and fallback.

## 5. POC source activation rule
Phase 1 activates only sources whose automated use is explicitly permitted or otherwise rights-cleared for the exact method/fields used. Open-access institutional APIs are preferred to exercise the real network/data pipeline immediately. Market/transaction sources are added only after their access method and rights are documented.

The current open-data collectors are operational-validation sources, not substitutes for market-price intelligence.

## 6. Vertical intelligence model
Architecture:
Universal Intelligence Core
-> Vertical Intelligence DNA
-> Vertical Source Graph
-> Vertical WHY Model
-> Vertical Score
-> Cross-Category Normalization
-> Kidult 100

Each vertical owns its own value-forming variables. Examples:
- Automobiles: production, specification, originality, provenance, mileage/condition, transaction history, concours/canon.
- Watches: reference, variation, serial/production range, condition, completeness, provenance, auction/dealer market.
- Toys & Models: edition/run, sealed/completeness, population, franchise persistence, transaction and collector demand.
- Fashion: designer/era, runway significance, production scarcity, cultural adoption, resale/auction, institutionalization.
- Design & Furniture: designer, manufacturer, edition, provenance, condition, institutional canon, auction/dealer market.
- Technology & Cameras: generation, production, technical significance, originality, condition, enthusiast canon, market.
- Gaming/Music/Screen: edition/issue, creator/franchise significance, grading/condition, cultural reach, transactions.
- Cards/Comics/Memorabilia: print/run/population, grade, subject canon, event significance, transactions, liquidity.

## 7. Data-quality gates for index-eligible evidence
- critical provenance: 100%
- rights classification: 100%
- entity resolution target: >=99.5%
- duplicate contamination: <0.5%
- asking vs sold classification: 100% where applicable
- currency/time normalization: 100% where applicable
- material rank/score change with WHY evidence: 100%
- derived signal confidence attached: 100%
- unknown or unsupported fields remain unknown; no fabricated proxy

## 10. UI stability contract
1. DATA DOES NOT DEFINE NAVIGATION.
2. Product capability is registered in a stable information architecture.
3. Missing data changes module state, not page geometry.
4. New verticals plug into the same Object / Compare / Discovery / Collection grammar.
5. New intelligence products use a Product Registry with placement rules rather than bespoke homepage redesign.
6. Desktop and mobile share the same information hierarchy; mobile changes layout, not meaning.
7. Collector and institution experiences share the intelligence core but can expose role-specific workspaces.

## 11. Product Registry contract
Every new product declares:
- productId
- customer: collector / institution / both
- questionAnswered
- decisionValue
- requiredPrimitives
- supportedVerticals
- confidence requirement
- rights requirement
- portalSlot
- entitlement
- update cadence
- evidence link

Only then can it appear in the portal.

## 12. Prototype states
The prototype must support four states without redesign:
- DEMO/SYNTHETIC
- REAL OPEN DATA
- RIGHTS-CLEARED MARKET DATA
- PRODUCTION INTELLIGENCE

Every card/module visibly inherits evidence/confidence state internally; public UX may simplify labels but may not misrepresent evidence class.

## 13. Immediate execution order
P0-A: Freeze this portal shell and product registry.
P0-B: Build >=300 Candidate Registry skeleton with vertical/category metadata.
P0-C: Build Source x Vertical x Primitive x Rights matrix.
P0-D: Activate rights-cleared external sources and collect >=100 candidates repeatedly.
P0-E: Produce first real Observation -> Signal -> WHY evidence chain.
P0-F: Bind real POC output to the stable future portal prototype without redesigning navigation.
P1: Add market/transaction channels as rights are cleared.
P1: Expand candidate universe toward 400-500 and begin cross-category normalization experiments.

## 14. Definition of success
The POC succeeds when KIDULTS can repeatedly ingest real external observations for >=100 candidates, preserve rights/provenance, survive source defects, generate at least one evidence-backed vertical signal and WHY explanation, and render it into the frozen portal shell without changing the information architecture.

The portal prototype succeeds when future products can be added through registry/configuration and module states rather than structural redesign.
